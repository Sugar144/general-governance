Findings

FIND-001 — BLOCKING — Tracked symlinks let excluded governance/** (or any operational) content be silently baked into RELEASE_INCLUDED bytes, defeating Gate B isolation
- Surface: tools/release_payload.py:77-81 (file_digest, uses Path.read_bytes()), tools/release_payload.py:269-280 (_digest_paths, no symlink check before dereferencing), tools/release_payload.py:306-339 (build_projection, copies via source_path.read_bytes() and writes a plain file, silently losing symlink-ness).
- Reproduced independently: I created a fresh git repo with a tracked symlink tools/evil.py -> ../governance/secret.txt (git stores this as mode 120000, blob content = the literal target string ../governance/secret.txt). classify_path("tools/evil.py", …) correctly returns RELEASE_INCLUDED (protected tools/ prefix). But content_digest() and build_projection() both call Path.read_bytes(), which follows the symlink and reads the target's bytes — i.e. the governance file's real content — not the git blob content of the symlink itself. Running the actual CLI (tools/release_payload.py project then verify-projection) confirmed: the built projection's tools/evil.py physically contains "TOP SECRET GOVERNANCE CONTENT" (copied straight out of governance/secret.txt), the symlink is materialized as an ordinary file, and verify-projection prints PASS: isolated release-payload projection integrity — because the digest recorded in the index was computed the same (dereferencing) way, so everything is internally self-consistent even though it no longer reflects the actual Git-tracked content of the path.
- Why this violates the accepted architecture/Issue #20 requirements: it directly falsifies three of the review's named required properties — "exclusion rules cannot be bypassed using … symlink-like … adversarial paths," "hidden dependencies on governance/** or other excluded operational content cannot survive Gate B," and "projection creation/verification detects omission, addition, mutation or misclassification." docs/architecture/release-payload-identity.md §7 states Gate B "runs … with operational files and .git physically absent. If included code requires excluded operational bytes, Gate B fails." That guarantee does not hold: operational bytes don't just get referenced, they get copied wholesale into the payload under an innocuous included filename, undetected. The underlying read_bytes()-follows-symlinks helper predates I1 (baseline tools/validate_consumer.py:65-66 had the same behavior), but I1 is what introduces the operational/release isolation property and the Gate B isolation claim that this defeats, and it is squarely inside I1's authorized surface (tools/release_payload.py).
- Bounded correction recommendation (not implemented): reject tracked symlinks in tracked_paths()/classify_path()/_digest_paths()/build_projection() (detect via os.path.islink() or git ls-files -s mode 120000) — either fail closed on any tracked symlink under a RELEASE_INCLUDED path, or hash/copy the symlink's literal target-path bytes (matching Git's own blob semantics) rather than dereferencing through the filesystem.
